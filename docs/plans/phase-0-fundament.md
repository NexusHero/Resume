## 1. Ziel

Nach Phase 0 ist myJob ein Bewerbungsservice mit einer klaren, ehrlichen Oberfläche, auf der die späteren Phasen (Stellen, Bewerbung, Magic Pen, Abschluss, Agent) aufbauen:

1. **Workspace-Schalter `vermittlung`** (Standard aus für alle Workspaces, pro Workspace, nur von Workspace-Admins umlegbar). Aus bedeutet: alle Vermittler-Routen antworten 404 `problem+json`, die Navigation zeigt nur Workspace, Mandanten, Stellen, Bewerbungen und Einstellungen (Desktop und Mobil), geplante Vermittler-Jobs überspringen den Workspace. Die Daten bleiben unberührt. Beim Serverstart warnt das Log pro Workspace, der Vermittler-Daten hat, aber ausgeschaltet ist.
2. **Neue Begriffe in der gesamten UI** (Mandant, Suchauftrag, Workspace, Stelle, Bewerbung), belegt durch einen Test gegen eine Verbotsliste.
3. **KI nur über einen zentralen Server-Key** (`ANTHROPIC_API_KEY`, optional `GEMINI_API_KEY`), **ohne Ersatz-Text**: ohne Key antwortet jede KI-Route mit 503 `ai-not-configured`, jeder KI-Button zeigt „KI nicht eingerichtet“ und sendet nichts. Ein Anbieterfehler ist ein 502, nie ein stiller Template-Text. **Ausnahme (Owner-Entscheidung):** der CV-Import läuft ohne Key als ausdrücklich benannter Modus „Text übernehmen (ohne KI)“: der volle CV-Text wird gespeichert, es gibt keine Strukturierung und kein Parsen.
4. **Per-User-API-Keys entfallen** (Routen, Store, Verschlüsselung, UI); gespeicherte Keys werden idempotent gelöscht (fs: Datei, sql: Zeilen; die leere Tabelle bleibt für ein Release stehen, Expand/Contract).
5. **Doku**: ADR 0057 (liegt vor), Requirements, Architektur (+UML), OpenAPI, Changelog, Deployment.

## 2. Nicht-Ziele

Ausdrücklich **nicht** Teil von Phase 0:

- Die Entität `JobPosting` / „Stelle speichern“, Stellen-Liste, „Stelle einfügen“ per URL oder Text (Phase 1). Der Menüpunkt **Stellen** zeigt in Phase 0 die bestehende Stellensuche (`Matching`), umbenannt und umverdrahtet.
- Bewerbung = Stelle × Mandant, Dokumentkopie, Bewerbungs-Editor, Entfernen des `ApplyModal` (Phase 2). Das `ApplyModal` bekommt nur die neuen Begriffe und die KI-Sperre.
- Magic Pen, Mappe als ZIP/PDF mit neuem Dateinamen, Statusverlauf, Chat-Agent (Phasen 3 bis 5).
- Weiterentwicklung der Vermittler-Funktionen. Erlaubt sind nur: der Schalter (Guard, Metadaten, Test-Setup), die Vokabular-Änderung in ihren UI-Texten und die KI-Policy (kein Template, 503/502), soweit sie dieselben Services nutzen.
- Kein Umbenennen von Code-Bezeichnern, Routen (`/mandates`, `/talents`), Dateien oder Datenbankspalten. Nur UI-Texte und Doku ändern sich; neue Dateien tragen die neue Sprache (`workspace-settings`).
- Kein Pro/Free-Umbau (ADR-0021 bleibt: Pro-Routen bleiben Pro), kein neues Metering-Modell, kein neuer Auth-Mechanismus.
- Keine Änderung der Retention-/DSGVO-Routen, der Mitglieder-/Einladungs-/Super-Admin-Routen, der Bewerbungs-Routen (`/applications`), der Job-Suche (`/jobs`, `/searches`), der Dokument-Routen außer den unten benannten KI-Routen, der deterministischen ATS-Analyse (`POST /ats`).
- Keine Änderung am Modell-Standardwert in `server/src/config.ts` (eigenes Issue #310). Dokumentiert wird nur, dass `ANTHROPIC_MODEL` und `GEMINI_MODEL` Betriebsparameter sind.
- **Keine Handänderung an `design/myjob/_ds_bundle.js`** (generiert, `design/myjob/readme.md` verbietet es). Die Wortmarke wird über die Props gesteuert, siehe 3.6.
- Kein Umbenennen unter `design/myjob/` außerhalb von `ui_kits/recruiting/` (`screens/`, `templates/`, `decisions/` sind Design-Archiv und werden nicht ausgeliefert).
- Keine Änderung der Coverage-Schwellen (Jest 90 %), keine Abschwächung bestehender Tests.
- Keine Änderung an `/searches*` (heute instanzweit statt workspace-gebunden); das wird unter den Risiken vor Phase 1 zur Klärung vermerkt (RI15).

### 3.5 Nest-Module, Controller, Guards (`server/src/nest/`)

**Invariante der Guard-Reihenfolge (vom Drift-Test geprüft):** `AuthGuard` steht zuerst, `VermittlungGuard` direkt danach, `AiConfiguredGuard` steht vor `AiRateLimitGuard` und vor `PlanGuard`; die Reihenfolge von `AiRateLimitGuard` und `PlanGuard` untereinander ist frei. **Bewusste Ausnahme:** R33 (`dossier.pdf`) und R37 (`agg-rewrite`) haben bereits einen Methoden-`AiRateLimitGuard`, ihre effektive Kette ist `Auth, Vermittlung, Plan, RateLimit`, was die Invariante erfüllt. Zu den Klassen eingefrorener Controller wird **kein** Rate-Limit hinzugefügt.

**Grundregel Guard-Reihenfolge.** Nest führt Guards in der Reihenfolge global, Klasse, Methode aus (`@nestjs/core/helpers/context-creator.js`). Ein Methoden-Guard läuft also nach allen Klassen-Guards. Deshalb stehen **alle** Guards eines Controllers in **einer** festen Liste an der **Klasse**, und die Wirkung pro Route steuern Metadaten (`@RequiresVermittlung()`, `@RequiresAi()`). Ein Guard ohne Metadaten ist ein No-op. Feste Liste: `AuthGuard, VermittlungGuard, AiConfiguredGuard, AiRateLimitGuard, PlanGuard` (Controller nehmen die Teilmenge, die sie brauchen, in dieser Reihenfolge).

```ts
export interface WorkspaceSettings {
  /** Recruiter functions (Suchaufträge, pipeline, placements, …) are reachable. Default off. */
  vermittlung: boolean;
}
export const DEFAULT_WORKSPACE_SETTINGS: WorkspaceSettings = { vermittlung: false };
```

- **Schlüssel** ist die Scope-ID des Workspaces (`req.tenantId`, im Einzel-Tenant-Betrieb `team`). Eine Spalte an `tenants` reicht nicht: der implizite Workspace `team` hat keine Zeile dort (`TenantService` synthetisiert sie). Deshalb eine nach Scope geschlüsselte Struktur wie `retention_policies`.
- **Lesen** ist `{ ...DEFAULT_WORKSPACE_SETTINGS, ...stored }`; neue Felder in späteren Phasen brauchen keine Migration.
- **fs:** `archive/bewerbungen/workspace-settings.json`, Inhalt `{ "team": { "vermittlung": true } }`; Pfad aus `config.workspaceSettingsFile`.
- **sql** (in `runMigrationDdl`, unter dem Advisory-Lock):

  ```sql
  CREATE TABLE IF NOT EXISTS workspace_settings (
    workspace_id text PRIMARY KEY,
    settings jsonb NOT NULL
  );
  ```

  und in `schema.ts` `workspaceSettings = pgTable('workspace_settings', { workspaceId: text('workspace_id').primaryKey(), settings: jsonb('settings').$type<WorkspaceSettings>().notNull() })`.

- **Bestehende Workspaces (Owner-Entscheidung Q1):** Vermittlung ist für **alle** Workspaces aus, kein Backfill. Damit das nicht still passiert, ruft `index.ts` nach dem Start `logHiddenVermittlerData` auf: für jeden Scope aus `tenantScopes()`, dessen Schalter aus ist und der Suchaufträge oder Platzierungen hat, schreibt der Server eine Warnung `{ scope, mandates, placements }` mit dem Text „Vermittlung is off for this workspace but it holds recruiter data; enable it under Settings, Workspace.“ Der Upgrade-Hinweis steht im Changelog (3.8). Die Daten erscheinen nach dem Einschalten unverändert (AK-0.2).

### 4.2 Löschen der Per-User-Keys (AK-0.7) — Expand/Contract

Ein `DROP TABLE api_keys` im selben Release würde alte Instanzen einer Rolling Deploy brechen (`llm-feature-runner.ts` liest die Tabelle bei jedem KI-Aufruf und endet in einem 500) und die DSGVO-Löschung eines Kontos abbrechen (Schritt „api-keys“). Deshalb:

| ----- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------- |
| sql   | Die Tabelle bleibt in der DDL (`CREATE TABLE IF NOT EXISTS api_keys`), danach `DELETE FROM api_keys;` unter dem Migrations-Lock. Neuer Code liest und schreibt die Tabelle nie. - `users.llm_provider` (Provider-Wahl, ADR-0011) bleibt. Eine gespeicherte Wahl, die nicht verfügbar ist, wird beim Auflösen übersprungen, und `GET /settings/llm` meldet den **effektiven** Anbieter.

- Der Integrationstest (6.2) belegt: nach `migrate` sind die Zeilen weg **und** ein Lesezugriff auf `api_keys` gelingt weiter.

### 4.4 Textmodus-Import: Datenmodell (kein neues Schema im Store)

- **Ablageort des vollen Textes:** `resume.rawText` im bestehenden Dokument des Mandanten (`TalentDocuments.resume`). `resume` liegt in sql als `jsonb` (`talent_documents.resume`) und in fs im JSON der Dokumentdatei, deshalb ist **keine DDL- und keine Dateimigration** nötig; fehlt das Feld in Altbestand, gilt der zod-Default `''`. Grenze 50.000 Zeichen (gleich der bestehenden Grenze in `parsePdf`); darüber wird abgeschnitten und `truncated: true` gemeldet.
- `rawText` wird weder im CV-PDF noch in der Vorschau gerendert, nur im Editor als Feld „Importierter Text (ohne KI)“ angezeigt, aus dem der Nutzer Stationen und Skills von Hand übernimmt.
- **PDF als Anhang:** Beim **Massenimport** (`talents/import`) legt der Server das PDF im Textmodus sofort über den `AttachmentService` ab (Tabelle `attachments`, Grenze 15 MB), denn dort gibt es kein „Verwerfen". Beim **Editor-Import** (`parse-pdf`) legt der Server **nichts** ab: der Editor lädt das PDF erst beim „Übernehmen" über `uploadAttachment` hoch, ein „Verwerfen" hinterlässt keinen Anhang. Ein erneuter Import desselben PDFs ersetzt den vorhandenen Anhang (gleicher Name und gleiche Größe: erst löschen, dann hochladen), damit keine Duplikate entstehen. Kein neues Schema.
- **Zusammenführung im Editor:** `mergeTextImport(current, imported)` füllt nur leere Felder; es überschreibt nie Profil, Kontakt, Erfahrung, Ausbildung oder Skills.
- Der Textmodus schreibt `resume.summary` nicht (das frühere Abschneiden auf 600 Zeichen im Kurzprofil entfällt).
- **Abgrenzung von `rawText` (interne Rohquelle mit allen Personendaten des CV):** _im Export ja_ (`GET /account/export` enthält die Dokumente, also auch `rawText`), _in Mappe, Rendering, Prompts und Datenbeilagen nein_, _bei Anonymisierung geleert_. Konkret:
  - **Anonymisierung:** Der Purger „documents" im Modus `anonymize` setzt `rawText = ''` (3.5); das Löschen eines Mandanten entfernt das Dokument ganz.
  - **ZIP-Mappe:** `renderDossierZip` bettet `withoutRawText(documents)` als `myjob-resume-data` ein.
  - **Alle Stellen, an denen Dokumente nach außen oder in ein Modell gehen** (per `grep` auf `JSON.stringify(…documents|resume)`, `documents.resume` und Spreads geprüft): `document-service.ts` ZIP-Beilage (**ändern**), `document-translate.ts` `translatePrompt` (**ändern**, serialisiert `resume` ganz), `application-builder.ts` Snapshot (Spread von `resume`, **ändern**), `documents-html.ts`/PDF-Rendering (nutzt benannte Felder, **Test sichert ab**), Prompts für Zusammenfassung, Anschreiben, Tailoring, ATS, Pitch, Outreach, Match-Erklärung, Interview-Kit und Prep (lesen nur benannte Felder wie `summary`, `experience`, `skillGroups`; **Property-Test sichert ab**). Der KI-Import selbst bekommt den Text, weil er seine Eingabe ist.
- **Altbestand:** Dokumente ohne `rawText` gelten als leer. Lesepfade laufen nicht durch zod; deshalb normalisiert `DocumentService.get` per `normalizeDocuments`, und jeder Leser, der das Repository direkt benutzt, behandelt `undefined` als `''`.

### 5.3 Mechanismus der Vermittlungs-Sperre

- `server/src/nest/vermittlung.guard.ts`:

  ```ts
  export const REQUIRES_VERMITTLUNG = 'requires:vermittlung';
  export const RequiresVermittlung = () => SetMetadata(REQUIRES_VERMITTLUNG, true);

  @Injectable()
  export class VermittlungGuard implements CanActivate {
    constructor(
      private readonly reflector: Reflector,
      @Inject(WORKSPACE_SETTINGS_SERVICE) private readonly settings: WorkspaceSettingsService,
    ) {}
    async canActivate(ctx: ExecutionContext): Promise<boolean> {
      const required = this.reflector.getAllAndOverride<boolean | undefined>(REQUIRES_VERMITTLUNG, [
        ctx.getHandler(),
        ctx.getClass(),
      ]);
      if (!required) return true; // no metadata: no-op
      const req = ctx.switchToHttp().getRequest<Request>();
      if (!(await this.settings.isVermittlungEnabled(currentScope(req)))) {
        throw new NotFoundError(FEATURE_NOT_ENABLED_DETAIL);
      }
      return true;
    }
  }
  ```

- **Pro Request** liest der Guard die Einstellung des Workspace aus dem Store (fs: JSON-Datei, sql: Primärschlüssel-Lookup). Kein Cache, damit ein Umlegen sofort in allen Instanzen wirkt.
- **Kein `APP_GUARD`:** globale Guards laufen vor `AuthGuard` und kennen den Workspace nicht.
- **Kein Methoden-`@UseGuards`:** Guards laufen global, Klasse, Methode. Ein Methoden-Guard liefe nach `PlanGuard`/`AiRateLimitGuard`/`AiConfiguredGuard` und ergäbe bei Pitch/Outreach 402, 429 oder 503 statt 404. Deshalb steht die ganze Kette an der Klasse und nur die Metadaten an der Methode.
- **Drift-Wächter** (6.1) liest per `Reflect.getMetadata` (Nest-Konstanten `PATH_METADATA`, `METHOD_METADATA`, `GUARDS_METADATA`) alle Controller aus `FEATURE_MODULES` und prüft: jede Route aus `VERMITTLER_ROUTES` existiert und trägt `RequiresVermittlung` (Methode oder Klasse), keine andere trägt es, und die **effektive** Guard-Liste (Klasse dann Methode) erfüllt die Invariante aus 3.5: Auth zuerst, Vermittlung direkt danach, AiConfigured vor RateLimit und Plan; die Reihenfolge von RateLimit und Plan ist frei (R33 und R37 sind die dokumentierte Ausnahme mit Methoden-RateLimit).
- **Scheduler:** `runAssistantTick` und `runReplySyncTick` (3.3) filtern per `filterVermittlungEnabled`. Die Retention-Automatik läuft unabhängig.
- **Ausschalten löscht nichts.** Kein Code fasst bei `PATCH` Daten an (Test `VermittlungSwitch_OffThenOn_DataIsUnchanged`).

### 5.4 Mechanismus der KI-Sperre

- `server/src/nest/ai-configured.guard.ts`: `RequiresAi()` setzt Metadaten; `AiConfiguredGuard` prüft sie (Methode vor Klasse), ruft dann `LlmService.hasAvailableProvider()` (rein Config, kein I/O) und wirft sonst `AiNotConfiguredError`. Ohne Metadaten No-op.
- **Zweite Schicht im Service** (Scheduler, Autopilot, spätere Aufrufer): `LlmFeatureRunner.resolveProvider` wirft `AiNotConfiguredError`; kein Pfad liefert Text, wenn die Auflösung scheitert. Die Textmodus-Import-Pfade wählen den Modus vorab und rufen den Runner nur im Modus `ai`.
- **Provider-Auflösung** (`LlmService.resolve(preferred)`): 1. gespeicherte Wahl des Nutzers, wenn der Anbieter einen Server-Key hat; 2. konfigurierter Standard (`LLM_PROVIDER`, sonst `claude`), wenn verfügbar; 3. jeder andere verfügbare Anbieter.
- **Fehler des Anbieters** werden im Runner zu `UpstreamProviderError` (502). Es gibt keine Rückfall-Texte.

### 5.5 Neue und geänderte Routen im Detail

**`GET /api/v1/settings/workspace`**: Guards `AuthGuard`, jede Rolle. 200 `{ "vermittlung": false }`. 401 ohne Login.

**`PATCH /api/v1/settings/workspace`**: Guards `AuthGuard`, `RolesGuard` mit `@Can('workspace', 'configure')` (nur Rolle `admin`; ein Super-Admin ohne Tenant-Rolle `admin` ist nicht berechtigt). Body:

```ts
export const updateWorkspaceSettingsSchema = z
  .object({ vermittlung: z.boolean() })
  .partial()
  .strict()
  .refine((v) => Object.keys(v).length > 0, 'at least one setting is required');
```

200 `{ "vermittlung": true }` (neuer Gesamtzustand). 400 `validation-error` (leer, falscher Typ, unbekanntes Feld). 401 ohne Login. 403 `forbidden` für `recruiter`. Nebenwirkung: `logger.info({ scope, userId, vermittlung }, 'workspace setting changed')`, kein Audit-Eintrag.

**`GET /api/v1/auth/me`, `login`, `register`, `accept-invite`:** unverändert (kein `workspace`-Feld).

**`GET /api/v1/settings/llm`** (Soft-Auth, geändert): `{ current, providers: [{ id, label, available }], configured }`. `configured` ist wahr, wenn mindestens ein Anbieter einen Server-Key hat. `current` ist der **effektive** Anbieter für den Aufrufer (`resolve(gespeicherte Wahl)`), `null`, wenn keiner verfügbar ist.

**`POST /api/v1/cover-letter`** (geändert, **Breaking Change**, Owner-Entscheidung Q11): verlangt Login (401 sonst); sonst K09. Im CHANGELOG unter „Changed (breaking)". Die OpenAPI-Beschreibung „open route with template fallback“ entfällt.
